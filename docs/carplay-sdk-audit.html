CarPlay SDK capability audit

react-native-audio-browser · August 2026 · audited against the iPhoneSimulator 26.2 SDK (runtime verifications on the 26.3 simulator) SDK headers · what the library doesn’t use yet, how consumers might use it, and what it would look like on screen.
API-shape note: the per-field naming in this audit (prefixed carPlay* hints, style values like rail) has been superseded by the Section Styling design — style declaration blocks (TrackStyle / SectionStyle extends TrackStyle) with unprefixed, family-scoped properties and a cascade. This audit remains the record of the SDK evidence, per-feature applicability, and the decision history; field names below are translated where practical and the design doc is authoritative where they disagree. Linked issues #125, #126 and #131 still carry their pre-block titles (carPlay* names) — they update at implementation.

How additions land in the TS API · decided — block-model revision

This panel originally recorded the prefixed-hint doctrine (carPlay* flat fields, promotion policy, per-field type-gating). That architecture was superseded by the Section Styling design; the surviving rules and their block-model forms:

  • Facts vs renderings. Cross-platform content and state facts are core Track fields (progress, explicit, favorited, live) — the library chooses their glyphs. Rendering declarations live in the style blocks (TrackStyle, inheritable / SectionStyle extends TrackStyle, container) — unprefixed, family-scoped (grid*, card*) by today's rendering scope, cascading track ?? section ?? default.
  • Placement is mechanical: Apple element parameter ⇒ inheritable; element class or item-level knob ⇒ container. Style kinds are mutually exclusive (display); orthogonal axes are properties.
  • Vendor prefixes are retired for style properties (the CSS -webkit- lesson); per-property @platform/@default/@see docs carry the support contract instead, and scope-broadening is the grid-gap → gap alias path. carPlay* naming remains for platform feature config that isn't styling (carPlaySiriListButton, carPlayNowPlayingActions #128, carPlayTabBadge #130, carPlayUpNextTitle #57) — affordances, not rendering declarations.
  • Version degradation: decorations drop before layout, where the layout is renderable at all; degradation is never an inversion of intent. Track.disabled — now a content fact with full behavioral weight (never plays anywhere) — renders grayed+inert where the surface can draw it and is hidden where it can't: never a normal-looking dead control. Style properties remain presentation-only and degrade to no-op.
  • Restraint is the pressure valve: the issues below are proposals, not commitments — a field lands when a consumer actually needs it.

Each card carries an Applies to row showing which presentation the knob can affect, in the library's style vocabulary: list means it works there, grid means that presentation cannot show it, tab bar marks a surface outside the section styles.

Already tracked elsewhere, so only summarized here: the per-track accessory symbol, rendered on list rows and grid tiles alike (#125, style.accessorySymbol), row-element subtitles (just shipped), the Siri assistant cell (carPlaySiriListButton), the playing-indicator location, and the now-playing button row — all already exposed or in flight.

1. List rows · CPListItem

Docs: CPListItem · playbackProgress · isExplicitContent · CPListItemAccessoryType

playbackProgress iOS 14+ never set EXPOSE — core field, tracked: #52

Header: “a fractional value between 0 and 1 to display a progress bar on this list item.”
Applies to listgridsingle-line CarPlay puts the bar on CPListItem rows only — no tile element carries progress. (Android Auto's completion extras are per-item and not style-limited.)

How you’d use it

{
  title: 'Ep. armchair-42',
  src: 'https://cdn.example/ep42.mp3',
  progress: 0.62   // resume state from your backend
}

Podcast and audiobook apps show how far the listener got, straight in the browse list. Android Auto has the same concept (completion-status/percentage extras), so this belongs in the core Track vocabulary rather than a carPlay* hint — one field lights up both car surfaces.

Simulator caveat: in the demo lab the bar renders in none of the variants (bare, +isPlaying, +trailing indicator) — but the playing-row treatment is known not to draw on some iOS/CarPlay-Simulator combos for any third-party app, so this is inconclusive. Whether the bar requires isPlaying (which would shrink the resume-bar use case to the active row on CarPlay, while Android Auto renders on any row) is a head-unit question.

isEnabled (rows & tile elements) iOS 15 / 26 never set IMPLEMENT — #126 (Track.disabled)

Grays out and deadens a row or tile.
Applies to listgridsingle-line Rows since iOS 15; every iOS 26 tile element has an enabled flag too.

Decided (review + design doc): Track.disabled — a content-state fact, not a style property (it swallows taps, which is interaction). Degradation is atomic: gray + inert together, or neither — a surface that can't draw the gray leaves the item fully enabled, never a normal-looking dead control. Use when the title carries the reason ("Available at 9 PM"); hard unavailability belongs in data (no src). Absorbs #126.

accessoryImage / accessoryType = .cloud iOS 14+ accessoryType hardcoded none/disclosure FOLDED INTO #125

Applies to listgridsingle-line Unified in #125 as style.accessorySymbol: rows render it via accessoryImage (trailing), grid tiles via accessorySymbolName (leading the title); gridWrap: false has no accessory slot.

The library derives none vs. disclosure-chevron from src/path — that stays internal; an explicit consumer symbol wins over the derived chevron (row accessoryImage takes precedence over accessoryType). Decided: accessoryType itself is never surfaced. Its three cases split into “already derived correctly” (.none/.disclosureIndicator), “meaningless without a download feature” (.cloud), and “everything a consumer could want”, which is accessoryImage’s job via #125 — exposing the enum would add API for zero expressible intent.

2. Tile elements · iOS 26 element family

Docs: CPListImageRowItem · Element · RowElement · ImageGridElement · CardElement · CondensedElement · GridElement

CPListImageRowItemCardElement — featured cards iOS 26+ entirely unused EXPOSE — style.gridTile: 'card'

Card with image (optionally full-height), title, subtitle, and a tint color that becomes the background or the gradient behind the text.
Applies to gridlist A tile treatment, not a style kind (see the design doc's rejected shapes #9): the container property gridTile: 'card' on a grid section, with the inheritable cardTint (per card or section-wide) and cardImage: 'normal' | 'background'.

How you'd use it

{
  "title": "Featured",
  "path": "/featured",
  "style": { "display": "grid", "gridTile": "card",
             "gridWrap": false },
  "children": [
    { "title": "Station of the Day", "subtitle": "Jazz FM",
      "path": "/featured/1", "artwork": "…",
      "style": { "cardTint": "#1e3a8a" } }

}

The classic editorial hero row — gridTile: 'card' + gridWrap: false, a composition the old styles-only model could not express. Pre-26 the treatment drops and the layout survives (legacy image row); Android Auto renders its grid. Full property semantics live in the design doc's ledger.

CPListImageRowItemCondensedElement — condensed tiles iOS 26+ entirely unused EXPOSE — style.gridTile: 'condensed'

Compact element: image + shape + title + subtitle + accessory symbol.
Applies to single-linegridlist A container property (style.gridTile: 'condensed') — not a style kind: density is an axis of the grid, with no cross-surface meaning. In the block model it is one value of the gridTile enum, mutually exclusive with 'card'. And not per-track: the item initializers are homogeneous per element family (imageGridElements: or condensedElements:) — one condensed cell inside a regular grid cannot render. Shape is an element parameter (per-item legal); condensed is an element class (container-wide).

style.gridTile: 'condensed' on a gridWrap: false or grid section renders its tiles with condensed elements on iOS 26+; everywhere else (pre-26, Android Auto, app UI) the hint is a full no-op — purely visual, so degradation is trivially safe. Composes with the other tile hints: condensed elements take imageShape (the predicted widening of style.imageShape, arriving as a hint combo instead of a new style) and accessorySymbolName — and they carry a subtitle slot, which regular grid tiles lack, making this currently the only way a wrapping grid can show subtitles. Note Apple documents only the word “condensed”: no layout, density, or row count is specified anywhere; wrapping is governed by the item-level allowsMultipleLines. What it actually looks like is an empirical lab question (the demo passes allowsMultipleLines: true).

imageShape: .circular iOS 26+ hardcoded .roundedRectangle TRACKED — #131

Mask applied to grid/condensed tile images: rounded rectangle or circle.
Applies to gridsingle-linelist iOS 26 grid tiles (and gridTile: 'condensed' tiles, whose elements also take a shape) only — the gridWrap: false row element and the pre-26 legacy image row have no shape parameter.

How you’d use it

{
  title: 'Results',
  style: 'grid',
  style.imageShape: 'circular',  // section default
  children: [
    { title: 'Miles Davis', ... },  // circular (inherits)
    { title: 'Kind of Blue',        // per-item override wins
      style.imageShape: 'rounded-rectangle', ... }
  ]
}

Circular is the standard presentation for people — artists, hosts, DJs — and shape ultimately encodes the kind of item (mixed grids legitimately render artists circular next to rounded albums), so the property cascades (track ?? section ?? page) with the library’s established precedence (track ?? section, as per-track style already beats section style on Android Auto). Under the block model both levels are the same inheritable property (style.imageShape, cascade track ?? section) — shape-follows-kind means a track rightly carries its shape wherever it travels. Named without “Grid”: Apple’s condensed element takes the same imageShape, so gridTile: 'condensed' tiles inherit the property and the name stays honest. “Image”, mirroring Apple’s imageShape — platform-passthrough hints keep the platform’s own term (like style.accessorySymbol ← accessorySymbolName, style.cardTint ← tintColor); the library’s Artwork vocabulary governs library-defined names, not passthroughs.

3. List template & sections · CPListTemplate / CPListSection

Docs: CPListTemplate · CPListSection · CPAssistantCellConfiguration · CPButton · CPGridButton

Enhanced section headers — headerSubtitle, headerImage, headerButton iOS 15+ only plain header string used EXPOSE — mostly internal

A section header can carry a subtitle, an image, and a real button.
Applies to listgridsingle-line The header lives on CPListSection and is item-agnostic — the current "tile sections are headerless" rule is the library's choice (title lives in the image-row item), not a platform limit. On iOS 26+ the row item's text may be nil, so tile sections can adopt the enhanced header too; pre-26 the legacy item requires its text, so tile sections keep title-in-item as the fallback.

How you’d use it

Little new API needed: sections already have title and subtitle (→ header/headerSubtitle). The button is an action slot, not navigation: the header docs are semantically silent, but CPButton’s lineage is the Contact template’s action buttons, and Apple’s canonical enhanced header is the Music-style collection header — art, title/artist, and a play/shuffle button. The library’s best-aligned use: play-the-section (queue scope already is the section, ADR 0006) — or a favorite/add action for followable collections. On iOS 26+ tile sections can adopt the same header (the image-row item going text: nil); pre-26 tile sections keep title-in-item.

View-all belongs elsewhere: with the button slot reserved for actions, the idiomatic view-all affordance for a list section is an appended “View all” row — exactly what the Android Auto boundary already does for tile sections with a path, so it’s the cross-platform-consistent answer too. Tile sections keep the header tap as a bonus.

Button-text caveat: headerButton is a CPButton (not CPTextButton), whose designated initializer requires an image — the guaranteed affordance is a glyph (e.g. play.fill). Its settable title is documented as “displayed only in templates that allow for custom titles”, with no word on the list-section header — whether a label renders is an empirical simulator question. Icon for certain, title optimistically.

headerGridButtons (CPGridButton strip in a list header) iOS 26+ entirely unused EXPOSE — likely canonical use

Applies to whole list page Template-level (above all sections) — independent of section styles. Dynamically updatable (headerGridButtons is a settable property); the system trims to maximumHeaderGridButtonCount.

Hypothesis — unproven: Apple Music’s CarPlay album page (iOS 26 simulator) shows “▶ Play” and shuffle buttons above the track list, and this API is the plausible public mechanism for that strip — but Apple’s own apps may use private chrome, so placement, labels, and the surrounding art header are all unconfirmed until we hardcode buttons in the example app and look (the same test that settled the accessory symbol). Taking the hypothesis: collection-page action buttons, not the genre-shortcut strip originally guessed. Maps onto the library with no new browse vocabulary: a page whose children are playable (album, playlist, station list) gets Play / Shuffle header buttons meaning “queue this page’s children from the top” — the page-level sibling of the per-section header play button, and the first real “play the whole album” affordance for browse pages. Could be largely library-internal (derived from the page shape), with a hint only to opt out or reorder. Unlike the per-section CPButton, CPGridButton takes titleVariants — the label is at least first-class in the API, though whether the header renders it is part of the same empirical check.

showsTabBadge iOS 14+ never set TRACKED — #130 (needs #129)

Applies to tab bar Per-tab, on the tab's icon — not on rows or tiles.

How you’d use it

tabs: [{
  title: 'New',
  path: '/new',
  carPlayTabBadge: true
}]

“Something new here” dot on a tab — new episodes, fresh recommendations. A boolean hint on the tab track, toggled by re-serving the tabs.

Verified (iOS 26.3 simulator, demo lab): mutating showsTabBadge on a presented template does not redraw the tab; updateTemplates: applies it — as the header silence predicted (contrast headerGridButtons, which documents dynamic update). So the hint must ride the tab-rebuild path. A badge-only toggle keeps the tab count equal, so it dodges the known selected-tab-reset wart of unequal-count rebuilds.

API (decided): declarative — carPlayTabBadge?: boolean | 'until-opened' on the tab track, applied whenever tabs (re)build. true is content-controlled (lit until the data clears it — the "live now" case); 'until-opened' declares unseen semantics, licensing the library to clear on tab open with session-scoped memory so tab re-serves don't resurrect the dot. Cross-session seen-ness is the server's job: the tab-content fetch as a free (but prefetch-confounded — Android Auto eagerly loads tabs) heuristic, or a tab-visit event (which promotes the previously low-priority didSelectTemplate exposure). Worst case with neither: the dot relights once per session — annoying, never wrong-direction.

Prerequisite — notifyTabsChanged(): today the only tabs re-serve trigger is invalidateAllContent() (drops every cache and refreshes every template — absurd for a dot flip); notifyContentChanged addresses paths, and tabs aren't one ('__tabs__' is an authoring sentinel, and the path machinery — cache invalidation, current-path re-navigation — doesn't apply). A dedicated no-arg notifyTabsChanged() in the notify family re-queries the tabs source and updates each surface. A favorites-style imperative overlay (setCarPlayTabBadges(paths)) was considered and deferred: legitimate under the client-owned-state precedent (setFavorites), but the declarative field covers server-tab consumers first; the overlay waits for a consumer with local seen-state.

CPNowPlayingMoreButton + consumer action sheets iOS 14+ unused; no sheet API exists TRACKED — #128

Applies to now playing Button row of the now-playing screen; the sheet it presents is modal over the whole CarPlay UI (one modal at a time).

How you’d use it

ios: {
  carPlayNowPlayingButtons: ['favorite', 'repeat'],
  // presence conjures the system ⋯ button, always trailing
  carPlayNowPlayingActions: (track) => [
    // declarative: dismiss, then navigate(path)
    { title: 'Go to the Artist', path: track.albumPath },
    { title: 'More Like This',  path: `/similar/${track.id}` },
    // imperative escape hatch
    { title: 'Report Problem',  onSelect: () => report(track) }
  ]
}

Shape (decided): the field declares the actions available for the playing track; the system CPNowPlayingMoreButton (⋯, Apple-drawn glyph) is merely how CarPlay surfaces them — so there is no 'more' entry in the buttons array, no button/handler split, and the buttons enum stays plain strings in the spec. The button renders last by library policy (Apple documents no ordering; keeping it non-configurable preserves the freedom to follow the platform convention). No provider → no button; the provider returning [] for a track hides it for that track. Actions are derived at tap time, per active track — never static config. Each is { title, path } (declarative navigation — pure data, handled natively, serializable so a server could one day supply a track's contexts over the wire) or { title, onSelect } (imperative) — the library's established static-or-callback duality. Generalizes the now-playing screen's single built-in navigation affordance (the albumPath album/artist line) to N destinations.

Interaction contract (decided): click-and-close, never modal chaining — one sheet, one selection, the library auto-dismisses before invoking the action (a consumer can never wedge the single modal slot). Sequencing composes from existing primitives after the close (play, favorite, navigate — which pushes onto the browse stack the same way the Up Next button does). If an action wants a submenu, it isn't a quick action — depth belongs in the tree, at a Path. Tracked as #128 (design settled, not scheduled).

Applies to session-wide A state signal, not tied to any surface; its effects show up on lists (truncation) and keyboards.

contentStyle (light/dark suggestion) iOS 13 / 15.4 unused; trait-based artwork instead LOW

Applies to session-wide Affects artwork/appearance everywhere at once — not per style or surface.

Day/night artwork already adapts via trait collections, artworkCarPlayTinted (becoming style.artworkRendering: 'stencil' in the block design), and declared { light, dark } artwork variants. 7. Ruled out · with reasons

Docs: CPSearchTemplate · CPVoiceControlTemplate · CPAlertTemplate · CPActionSheetTemplate · Requesting CarPlay entitlements

Search & voice templates ENTITLEMENT-BLOCKED

CPSearchTemplate and CPVoiceControlTemplate are outside the carplay-audio entitlement (navigation apps only) — presenting them throws. Siri via the assistant cell + INPlayMediaIntent (already implemented) is Apple’s sanctioned search path for audio apps.

Everything else assessed and passed over

  • tabSystemItem — SF-symbol tab artwork already covers iconography with more control.
  • CPAlertTemplate / CPAlertAction colors — subsumed by the action-sheet proposal (above); the library’s error surface already uses CPActionSheetTemplate internally.
  • templateWillAppear/WillDisappear — internal lifecycle detail, no consumer value.
  • carTraitCollection, image-size constants, display-ready init images — already used correctly throughout.
